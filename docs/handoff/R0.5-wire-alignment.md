# Handoff: R0.5, align Studio's requests with what rune-infer accepts

For an AI coding agent. Read all of it first. It is a small, targeted change: three code work packages and one docs package. Do not add features, do not refactor, do not touch the safety rules.

## 1. Why (verified facts, source: the rune-infer developer's answers of 2026-10-19 plus the raw responses they pasted)

| Topic | What rune-infer does | What Studio does today (`src-tauri/src`) | Result |
|---|---|---|---|
| Audio in chat | Accepts only `{"type":"input_audio","input_audio":{"data":"<base64>","format":"wav"\|"mp3"}}` (commit `9a34e50`, **unreleased**, on its `develop`). `audio_url` is not deserialised: **the audio is silently ignored**. Limits: wav/mp3, 50 MB decoded, no resampling, no duration limit. | `model/client.rs:78` sends `{"type":"audio_url","audio_url":{"url":"data:audio/wav;base64,..."}}` | Voice does not work against rune-infer. |
| Thinking | Honoured: `thinking: {"type":"disabled"}` and `reasoning_effort: "none"`. **Not** honoured: `chat_template_kwargs.enable_thinking`. | `model/client.rs:99` sends only `chat_template_kwargs.enable_thinking` | The "off" switch does nothing. A pasted reply with no thinking parameter contained `reasoning_content`, so thinking is probably **on by default** (**NOT CERTAIN**: ask). That would add hidden thinking tokens to every step. |
| `/v1/decisions` | Returns `{decision, probability}` (yes/no) and `{decision, confidence, probabilities}` (choice). The Postman `{type, value, confidence}` is legacy. Images are used. | `model/decision.rs` reads both shapes (R0) | Parser is fine. |
| Choice `confidence` | In the pasted answer: `decision: "blue_green"`, `confidence: 0.1374`, `probabilities: {immediate_switch 0.2555, canary_rollout 0.3196, blue_green 0.4249}`. `confidence` is **not** the top probability. | `agent/quick.rs` gates "high risk" on `confidence >= 0.8` (`RISKY`) | That threshold may be unreachable. Meaning of `confidence`: **NOT CERTAIN**. |
| `usage` | In pasted replies: prompt 786 = completion 786 for the audio call; prompt 1, completion 1 for a reply of "Four". | not used for decisions | `usage` is unreliable. Do not build on it. |

## 3. Work packages

### WP1: the chat request body (`src-tauri/src/model/client.rs`)

1. **Extract the body construction** out of `ChatClient::call` into a pure function you can unit test, e.g. `fn chat_body(model: &str, request: &Request<'_>) -> Value`. `call` must use it and behave exactly as before otherwise (URL, auth, timeout, streaming, parsing unchanged).
2. **Audio part.** Replace the `audio_url` part with
   ```json
   { "type": "input_audio", "input_audio": { "data": "<the base64 WAV>", "format": "wav" } }
   ```
   `request.audio` already holds the base64 of the whole WAV file (`voice/mod.rs` does `BASE64.encode(&wav)`); pass it unchanged as `data`. Keep the part order (audio, image, text). Do not send `audio_url` any more. Whether `data` should contain the WAV header or raw PCM is **NOT CERTAIN** (the developer said the server "passes the base64 audio directly to the engine"); keep sending the full WAV file and say so in the report.
3. **Thinking switch.** Add the top-level field `"thinking": {"type": "disabled"}` when `request.think` is false and `{"type": "enabled"}` when true. **Keep** `chat_template_kwargs: {"enable_thinking": request.think}` as it is (harmless to servers that read it). Do not add `reasoning_effort`, do not add `budget_tokens` (**NOT CERTAIN** whether `budget_tokens` is optional for `enabled`). Keep `max_tokens` as is (512 / 3000).
4. Update the module doc comment at the top of the file so it no longer says thinking is switched only by `chat_template_kwargs`.

Tests (in the same file, next to the existing ones), asserting the exact JSON:
- with audio, image and text: parts are `[input_audio, image_url, text]`, the audio part has `type`, `input_audio.data` equal to the input and `input_audio.format == "wav"`, and **no `audio_url` key anywhere** in the body;
- `think: false` -> `thinking == {"type":"disabled"}` and `chat_template_kwargs.enable_thinking == false`; `think: true` -> `{"type":"enabled"}`, `stream == true`, `max_tokens == 3000`;
- text-only request: `content` is a plain string; `tools` and `tool_choice: "required"` unchanged; `temperature == 0`.

Acceptance: `grep -rn "audio_url" src-tauri/src` prints nothing except inside tests that assert its absence; the existing tests in the file still pass.

### WP2: record what the decision model really says (`model/decision.rs`, `agent/quick.rs`), **no threshold changes**

Goal: collect data so the thresholds can be set from facts later.
1. In `model/decision.rs`, when an answer is read, log at `info` one compact line per question: question name, shape (`source`/`spec`), `decision`, `confidence`, `probability`, and for a choice the probability of the picked option (`probabilities[decision]`), e.g. `decision answer risk: decision=high confidence=0.14 p(high)=0.42`. No image data, no task text. Keep the existing "shape seen" one-time log.
2. Add a method that returns the probability of the picked option (`Option<f64>`) next to `choice()`. **Do not use it for any decision yet.** Behaviour of `confident_yes`, `choice` and every caller must stay identical.
3. Update the comment above the shapes: the running server returns the **source** shape (confirmed by the maintainer on 2026-10-19); the spec shape is legacy and kept only because it is harmless.
4. **Do not change** `SIMPLE_TASK`, `FINISHED`, `RISKY`, `LOADING`, `BLOCKER`.

Tests: the existing ones pass; one new test with the pasted raw answer `{"routing":{"decision":"blue_green","confidence":0.1374,"probabilities":{"immediate_switch":0.2555,"canary_rollout":0.3196,"blue_green":0.4249}},"requires_approval":{"decision":true,"probability":0.6816}}` asserting `choice("routing") == Some(("blue_green", 0.1374))`, the picked probability is `0.4249`, and `confident_yes("requires_approval", 0.68)` is true while `0.69` is false.

### WP3: tell the user when the server cannot hear (`backend.rs`, small)

`GET /v1/models` items carry a `capabilities` list (e.g. `["Chat","Vision","Audio","Video","Omni","Tool Call"]`).
1. In `backend.rs` parse `capabilities` (optional field, default empty) from the configured model's entry and add `model_capabilities: Vec<String>` to `BackendStatus` (camelCase in JSON) and to `BackendStatus` in `src/types/protocol.ts`. Nothing in the UI has to change.
2. In `commands::toggle_listening`, when the microphone is about to open, call the backend check; if the model **was listed and has no `"Audio"`**, log a `warn` ("the configured model does not list Audio: voice will not be understood") and carry on (do not block). If the list is empty or the check fails, say nothing.
Tests: parsing with and without the field; a helper `fn lacks_audio(&[String]) -> bool` (false when the list is empty).
